# Step 6 — Move violation-push logic into the V-tree module

## Background: what is the violation concept?

A V-node is **violated** when its intensity exceeds the maximum intensity of its
uncles (siblings of its parent) at the grandparent level.  This represents an
intensity imbalance in the V-tree that requires structural rebalancing.

The violation concept manifests at two layers:

| Layer | Item | Current home |
|---|---|---|
| `VNodeTree` | `is_violated(id)` predicate | `vnode_tree.rs` ✅ |
| `VNodeTree` | `max_uncle_intensity(id)` query | `vnode_tree.rs` ✅ |
| `VNodeTree` | `find_violated_nodes()` scan | `vnode_tree.rs` ✅ |
| `VTree` | `violations: Vec<VNodeId>` queue | `vtree/mod.rs` ✅ |
| `VTree` | `push_violation(id)` enqueue | `vtree/mod.rs` ✅ |
| `graph/algorithm` | `ViolationQueue` wrapper | `violation_push.rs` ❌ |
| `graph/algorithm` | `push_*` family (16 functions) | `violation_push.rs` ❌ |
| `graph/algorithm` | `ViolationSources` config | `violation_sources.rs` ❌ |

The predicate and queue already live in the right places.  The push helpers and
the config struct are in `src/graph/algorithm/`, which sits *above* `vtree` in
the ownership ladder — yet they only Access `VNodeTree` and `Vec<VNodeId>` and
have no dependency on `GvGraph`, `GvCore`, `Config`, or any graph-level type.

## Scope of violations

Violations are generated by **four** algorithms:

1. `observe` — after a direct observe call that creates the first V-node split
2. `split` — after a G-node split; three contraction violations may arise
3. `evict` — after removing a leaf from the V-tree
4. `rebalance/resolve` — when resolving one violation can expose others (escalation)

They are consumed exclusively by the rebalance algorithm.  The concept is
therefore a V-tree invariant enforced across multiple upper-layer algorithms,
not a detail of a single algorithm.

## Why `violation_push.rs` and `violation_sources.rs` belong in vtree

All functions in `violation_push.rs`:
- take `&VNodeTree<V>` as their first data parameter
- act on `Vec<VNodeId>` (the `violations` field of `VTree`)
- have no dependency on G-tree data, `Config`, or the graph layer

`ViolationSources` is a pure boolean config struct consumed only by `violation_push.rs`.

Moving these two files into `src/tree/vtree/` is consistent with the
*lowest-capable-type* rule from the migration vision: behaviour should live on
the lowest type whose data is sufficient.

## Circular-import analysis

Moving `violation_push.rs` naively creates a dependency cycle through `Nd`:

```
crate::tree::vtree::violation_push
  → crate::graph::algorithm::rebalance::Nd
  → crate::graph::algorithm::fmt::Nd            (re-exported by rebalance.rs)
  → crate::tree::vtree::VNodeTree
  → crate::tree::vtree                          ← cycle ❌
```

`Nd` is a debug-format wrapper that only depends on `VNodeTree`, `VNodeId`,
`VKind`, and `Accumulator` — all of which are btree-layer types.  It is a
vtree-level concern that accidentally ended up in the graph layer.

**Resolution**: move `Nd` to a new `src/tree/vtree/fmt.rs` and have
`graph/algorithm/fmt.rs` re-export it.  This is a conceptual improvement as
well: `Nd` is a vtree-specific formatter and belongs with vtree.

`Ctx` and `Ch` (also in `graph/algorithm/fmt.rs`) have the same vtree-only
dependencies but are used exclusively within `graph/algorithm` internals, so
they remain in place for now.

After moving `Nd`:
```
crate::tree::vtree::violation_push
  → crate::tree::vtree::fmt::Nd               ← same crate, no cycle ✓
  → crate::tree::vtree::VNodeTree              ← parent module via super ✓
  → crate::tree::vtree::vnode::VKind           ← sibling module ✓
  → crate::tree::vtree::violation_sources      ← sibling module (moved together) ✓
```

The existing callers in `graph/algorithm` that use `rebalance::Nd` continue to
work because `rebalance.rs` re-exports from `graph/algorithm/fmt.rs`, which
re-exports from `tree::vtree::fmt`.
